Como o frontend faz as requisições

Todas as chamadas passam pela função apiFetch em src/services/api.ts. Ela:

  • Adiciona o header Content-Type: application/json em todas as requisições
  • Adiciona o header Authorization: Bearer <token> se houver token no localStorage
  • Lança um erro com o texto do body da resposta se o status não for 2xx
  • Retorna undefined para respostas HTTP 204 (sem body)
URL Base: O frontend usa http://localhost:8080 por padrão. Pode ser sobrescrito com a variável de ambiente VITE_API_URL no arquivo .env do projeto frontend.

Ciclo de vida dos dados

O frontend não usa WebSocket nem SSE. Os dados são carregados ao montar o componente (useEffect) e, no Dashboard, atualizados a cada 30 segundos via setInterval. Não há atualizações em tempo real — polling simples.

Seção 2

Fluxo de Autenticação JWT

Como o frontend gerencia sessão, tokens e logout.

Fluxo completo

1
Usuário preenche email e senha

Frontend envia POST /api/auth/login com body { "email": "...", "senha": "..." }

2
Spring autentica e retorna JWT

Resposta: { "token": "eyJhbGciOiJIUzI1NiJ9..." }

3
Frontend armazena o token

O JWT é salvo no localStorage com a chave "healthsys_token"

4
Decodificação do payload

O frontend decodifica o JWT com atob(token.split('.')[1]) e extrai o campo sub (email do usuário). O displayName é o trecho antes do @.

5
Todas as requisições seguintes incluem o Bearer token

Header: Authorization: Bearer eyJhbGciOiJIUzI1NiJ9...

6
Logout

Remove o token do localStorage e recarrega a página. A sessão no servidor não precisa ser invalidada (stateless JWT).

Campo obrigatório no payload JWT: O frontend lê o campo sub do payload para identificar o usuário. O Spring já faz isso com jwtUtil.generateToken(loginRequest.getEmail()) — o campo sub é o padrão da spec JWT para "subject". Certifique-se de que o JwtUtil inclui sub ao gerar o token.

Exemplo do payload JWT esperado

{
  "sub": "medico@hospital.com",   // campo obrigatório — lido pelo frontend
  "iat": 1714150000,            // issued at (epoch)
  "exp": 1714236400             // expiration (epoch)
}

Recomendação: tratamento de token expirado

O frontend ainda não trata 401 automaticamente. Recomendamos adicionar no backend uma resposta clara ao token expirado e, futuramente, implementar o redirecionamento no frontend:

// Resposta sugerida para token expirado (Spring Security)
HTTP 401 Unauthorized
{
  "error": "Token expirado ou inválido"
}
Seção 3

Formato das Requisições e Respostas

Padrões que o frontend segue em todas as chamadas HTTP.

Headers enviados pelo frontend

Content-Type: application/json
Authorization: Bearer eyJhbGciOiJIUzI1NiJ9.eyJzdWIiOiJ1c2VyQGVtYWlsLmNvbSJ9.xxxx

O que o frontend espera nas respostas

SituaçãoStatus HTTPBody
Listagem com resultados200Array JSON: [ {...}, {...} ]
Listagem vazia200Array vazio: []
Criação bem-sucedida200 ou 201Objeto criado com id preenchido
Atualização bem-sucedida200 ou 204Objeto atualizado ou vazio
Erro de autenticação401Qualquer texto (será logado no console)
Erro de validação / negócio400 / 422Qualquer texto (será exibido na tela)
Erro interno500Qualquer texto
IDs como string ou número: O frontend trata o campo id como string nos tipos TypeScript, mas usa String(id) nas comparações. O Spring pode retornar Long que será serializado como número no JSON — isso é compatível, pois o JavaScript converte automaticamente ao comparar.

Serialização de datas

O frontend envia e espera datas no formato ISO 8601:

"2026-04-26T14:30:00.000Z"   // data + hora (Triage.data)
"1990-05-15"                  // somente data (Patient.dataNascimento)
Jackson no Spring Boot: Para que datas LocalDate e LocalDateTime sejam serializadas corretamente como string ISO no JSON, adicione ao application.properties: 
spring.jackson.serialization.write-dates-as-timestamps=false

POST /api/triage
🔒 Requer JWT

Registra uma nova triagem. O frontend envia os dados preenchidos no formulário de 3 etapas (identificação, sinais vitais, classificação).

Request Body

{
  "patientId": "42",                    // id do paciente selecionado
  "patientName": "Maria Silva",         // nome desnormalizado para exibição
  "nivelRisco": "Urgente",              // classificação Manchester
  "status": "Pendente",                 // sempre "Pendente" na criação
  "data": "2026-04-26T14:30:00.000Z", // new Date().toISOString()
  "vitals": {
    "temp": "37.2",                    // temperatura em °C (string)
    "heartRate": "85",               // frequência cardíaca em bpm (string)
    "saturation": "97",              // saturação O2 em % (string)
    "pressure": "120/80"             // pressão arterial (string livre)
  }
}
vitals como objeto embutido: O frontend envia os sinais vitais como um objeto JSON aninhado. O modelo Triage.java precisa aceitar isso — pode ser um objeto @Embedded, um JSON armazenado como String com @Column(columnDefinition = "TEXT"), ou um relacionamento separado. A escolha é livre, desde que o GET retorne no mesmo formato.
Status: Implementado — TriageController.java já existe. Verificar se o modelo Triage.java tem os campos patientId, patientName, nivelRisco, status, data e vitals.

Beds — Monitoramento de Leitos

Controller ainda não existe no backend. A tela de Monitoramento está pronta no frontend esperando estes dois endpoints.

Pendente: Criar BedController.java, Bed.java (model), BedRepository.java e BedService.java seguindo o mesmo padrão dos outros controllers.
GET /api/beds
🔒 Requer JWT

Retorna todos os leitos. O frontend agrupa por setor e ordena alfabeticamente.

Response esperado — 200 OK

[
  {
    "id": "A01",               // string ou number — identificador do leito
    "setor": "UTI Adulto",     // nome do setor — usado para agrupar na tela
    "status": "Disponível",    // "Disponível" | "Ocupado" | "Manutenção"
    "pacienteId": null         // id ou nome do paciente, se ocupado
  },
  {
    "id": "A02",
    "setor": "UTI Adulto",
    "status": "Ocupado",
    "pacienteId": "João Souza"
  },
  { ... }
]

Campos obrigatórios

Campo JSONTipoObrig.Observação
idstringobrigatórioExibido como rótulo do card de leito (ex: "A01", "B12")
setorstringobrigatórioNome do setor. Leitos do mesmo setor são agrupados
statusstringobrigatórioExatamente: "Disponível", "Ocupado" ou "Manutenção"
pacienteIdstring / nullopcionalNome ou ID do paciente. Exibido quando status = "Ocupado"
Atenção ao nome do status: O frontend usa esses três valores exatos com acentuação para mapear cores. Se o backend retornar "Disponivel" (sem acento) ou "available", o card aparecerá sem cor. Manter exatamente: "Disponível", "Ocupado", "Manutenção".
PUT /api/beds/{id}
🔒 Requer JWT

Atualiza o status de um leito. Chamado quando o usuário clica em um leito e altera seu status no modal.

Request Body

{
  "status": "Ocupado",
  "pacienteId": "Novo Paciente"   // ou null se status != "Ocupado"
}

Response — 200 OK

{
  "id": "A01",
  "setor": "UTI Adulto",
  "status": "Ocupado",
  "pacienteId": "Novo Paciente"
}

Controller sugerido

@RestController
@RequestMapping("/api/beds")
@CrossOrigin(origins = "*")
public class BedController {

    @Autowired
    private BedRepository bedRepository;

    @GetMapping
    public List<Bed> getAll() {
        return bedRepository.findAll();
    }

    @PutMapping("/{id}")
    public Bed update(@PathVariable Long id, @RequestBody Bed bed) {
        Bed existing = bedRepository.findById(id).orElseThrow();
        existing.setStatus(bed.getStatus());
        existing.setPacienteId(bed.getPacienteId());
        return bedRepository.save(existing);
    }
}

Seção 10

CORS

Configuração necessária para o browser permitir as requisições do frontend para o backend.

Configuração atual (desenvolvimento)

Os controllers existentes já têm @CrossOrigin(origins = "*") que permite qualquer origem. Isso funciona para desenvolvimento local.

Configuração global recomendada

Em vez de anotar cada controller individualmente, criar uma configuração global:

@Configuration
public class CorsConfig implements WebMvcConfigurer {

    @Override
    public void addCorsMappings(CorsRegistry registry) {
        registry.addMapping("/api/**")
            .allowedOrigins(
                "http://localhost:5173",   // Vite dev server (padrão)
                "http://localhost:4173"    // Vite preview
            )
            .allowedMethods("GET", "POST", "PUT", "DELETE", "OPTIONS")
            .allowedHeaders("*")
            .allowCredentials(false);
    }
}
Spring Security + CORS: Se o projeto usa Spring Security, o CORS precisa ser configurado também no SecurityFilterChain, pois o Spring Security intercepta antes do WebMvcConfigurer: 
@Bean
public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
    http
        .cors(Customizer::withDefaults)  // usa o CorsConfig acima
        .csrf(csrf -> csrf.disable())
        .authorizeHttpRequests(auth -> auth
            .requestMatchers("/api/auth/**").permitAll()
            .anyRequest().authenticated()
        )
        .addFilterBefore(jwtFilter, UsernamePasswordAuthenticationFilter.class);
    return http.build();
}
Preflight (OPTIONS): Navegadores enviam uma requisição OPTIONS antes de POST/PUT com headers customizados. Certifique-se de que o /api/auth/login e demais endpoints respondem corretamente ao OPTIONS (status 200 ou 204).
Seção 11

Tratamento de Erros

Como o frontend reage a cada tipo de resposta de erro.

HTTP StatusSituaçãoComportamento no frontend
400Dados inválidosExibe o texto do body no console. Em Login, exibe "Email ou senha inválidos."
401Não autenticado / token inválidoLança erro (não trata automaticamente ainda — recomendado implementar redirecionamento)
403Sem permissãoLança erro com o texto do body
404Recurso não encontradoLança erro com "HTTP 404"
500Erro interno do servidorLança erro — capturado pelo ErrorBoundary e exibe tela de erro

Formato de erro recomendado

O frontend aceita qualquer texto no body de erro. Para facilitar depuração, recomendamos o padrão Spring:

{
  "timestamp": "2026-04-26T14:30:00Z",
  "status": 400,
  "error": "Bad Request",
  "message": "Campo 'nome' é obrigatório",
  "path": "/api/patients"
}
Global Exception Handler: Recomendamos criar um @ControllerAdvice para padronizar as respostas de erro em todos os controllers.
