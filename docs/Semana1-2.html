1 Definição dos Requisitos do Sistema

O HealthSys é uma plataforma de gestão hospitalar distribuída que automatiza os principais fluxos de um ambiente hospitalar: cadastro de pacientes, triagem, prontuários eletrônicos, gestão de leitos e controle de usuários. O sistema é construído sobre uma arquitetura de microsserviços, garantindo escalabilidade e independência entre os domínios.

1.1 Requisitos Funcionais

👤 Gestão de Usuários

  • Cadastro de usuários com perfis: Admin, Médico e Enfermeiro
  • Autenticação via login com e-mail e senha
  • Geração de token JWT após autenticação bem-sucedida
  • Listagem, criação e remoção de usuários
  • Carga inicial automática de usuários padrão (DataSeeder)

🏥 Gestão de Pacientes

  • Cadastro de pacientes com dados pessoais completos
  • Armazenamento de nome, data de nascimento, sexo, telefone e e-mail
  • Listagem e busca de pacientes cadastrados
  • Atualização e remoção de registros de pacientes

🩺 Triagem

  • Registro de triagem vinculada a um paciente
  • Classificação de risco (ex.: verde, amarelo, vermelho)
  • Coleta de sinais vitais: temperatura, frequência cardíaca, saturação e pressão arterial
  • Controle de status da triagem (aguardando, em atendimento, concluída)
  • Publicação de eventos de triagem no Kafka para integração assíncrona

📋 Prontuário Eletrônico

  • Criação de registros de prontuário por paciente
  • Associação de tipo de atendimento, médico responsável e data
  • Listagem de prontuários para consulta clínica
  • Acesso restrito por autenticação JWT

🛏️ Gestão de Leitos

  • Cadastro de leitos com identificador, setor e status
  • Atualização de status: disponível, ocupado, em manutenção
  • Vinculação de leito a um paciente internado
  • Listagem em tempo real dos leitos e suas ocupações

🔐 Segurança e Acesso

  • Todas as rotas protegidas requerem token JWT válido
  • Rota de login pública (/api/auth/login)
  • Validação centralizada do JWT no API Gateway
  • Propagação do e-mail autenticado via header X-User-Email

1.2 Requisitos Não Funcionais

⚡ Desempenho e Escalabilidade

  • Cada microsserviço é escalável de forma independente
  • Comunicação assíncrona via Apache Kafka para operações de alto volume
  • Sessões stateless (JWT) — sem dependência de estado no servidor
  • Pool de conexões com banco de dados gerenciado pelo HikariCP

🛡️ Segurança

  • Autenticação baseada em JWT com expiração de 10 horas
  • Senhas armazenadas com BCrypt (fator de custo padrão)
  • CSRF desabilitado para APIs REST stateless
  • CORS configurado apenas para origens autorizadas

🔧 Manutenibilidade

  • Arquitetura de microsserviços: cada serviço com repositório e deploy independente
  • Containerização com Docker e orquestração via Docker Compose
  • Separação clara por domínio (DDD aplicado por serviço)
  • Configuração externalizada via variáveis de ambiente

📡 Disponibilidade e Integração

  • API Gateway único como ponto de entrada para o frontend
  • Health checks no PostgreSQL e Kafka via Docker Compose
  • Serviços dependentes aguardam infraestrutura estar pronta (depends_on)
  • Banco de dados centralizado PostgreSQL 16 com schemas independentes por domínio

2 Modelagem da Arquitetura Distribuída

O HealthSys adota o padrão de microsserviços com um API Gateway central que recebe todas as requisições do frontend, valida o token JWT e as roteia para o serviço responsável. A comunicação entre serviços ocorre de forma assíncrona via Apache Kafka quando necessário (ex.: criação de triagem).

3 Modelagem Inicial do Banco de Dados

O banco de dados utilizado é o PostgreSQL 16. Todas as tabelas residem no mesmo schema (healthsys/public), porém cada microsserviço acessa exclusivamente as tabelas do seu domínio, garantindo isolamento lógico. O Hibernate gerencia a criação e atualização das tabelas via ddl-auto: update.

Relacionamentos entre Entidades

Patient ──(1:N)── Triage (um paciente pode ter múltiplas triagens) referência via patient_id (chave lógica, sem FK física entre serviços) Patient ──(1:N)── MedicalRecord (um paciente pode ter múltiplos prontuários) Patient ──(1:1)── Bed (um paciente pode estar internado em um leito) Triage ──(1:1)── Vitals (sinais vitais embutidos na triagem — @Embeddable)

⚠️ Em arquitetura de microsserviços, não existem foreign keys físicas entre serviços distintos. As relações são mantidas via chaves lógicas (IDs referenciados como VARCHAR/BIGINT) e a consistência é garantida pela camada de aplicação ou por eventos no Kafka.
